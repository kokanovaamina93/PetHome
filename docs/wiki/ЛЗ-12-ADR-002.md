# ADR-002. Включаем ли интеллектуальный подбор питомца

| Поле ADR | Содержание |
|---|---|
| **Статус** | **Отложено (не принято), 25.11.2026.** Решение: развиваем гибридный подбор, но для реальных пользователей НЕ включаем — критерий приёмки не выполнен. На сайте функция работает в учебном режиме с уведомлением об ИИ, переключатель доступен сотрудникам. Пересмотр — после промпта v3 и повторного независимого замера |
| **Контекст** | Пользователь выбирает животное вручную из каталога, фильтры не учитывают сочетания условий. Backend размещён на Render Free (512 МБ ОЗУ, засыпает через 15 минут), frontend — на Vercel; сайт должен работать без компьютера команды. Замер 24–25.11.2026 на 36 сценариях (все выполнены; 8 ответов 429 повторены после паузы): baseline из 18 правил — macro F1 0,504, NDCG@5 0,853; итоговый гибрид D2 — macro F1 0,682, NDCG@5 0,604, нарушений ограничений 23,6 %. На эталоне v2 (согласованные разметки Фаризы и Амины) D2 — macro F1 0,406 против 0,385 у baseline, но хуже по классам «Подходит» и «Не подходит», NDCG@5 0,138 против 0,378, нарушений 31,9 % |
| **Рассмотренные варианты** | 1) Не внедрять интеллектуальный подбор. 2) Только правила (вариант A). 3) Только внешний облачный API (Groq, openai/gpt-oss-20b), варианты B/C. 4) Открытая модель на собственном сервере (Hetzner CPX42 или GEX45). 5) Гибрид: облачная модель + проверка обязательных ограничений правилами + правило отказа + правила как резерв (D/D2) |
| **Решение** | Вариант 5 (гибрид D2) как архитектура; включение для реальных пользователей отложено. Модель только подсказывает: заявку одобряет сотрудник, есть уведомление об ИИ, переключатель без остановки сайта (PATCH /admin/ai), при недоступности модели — подбор по правилам с отдельным уведомлением и указанием причины |
| **Почему не вариант 1** | Без подбора пользователь сам сопоставляет 8 фильтров и не может описать ситуацию своими словами; отказ от функции не снижает риск неподходящих заявок |
| **Почему не вариант 2** | Правила лучше всех ранжируют (NDCG@5 0,853), но плохо различают «недостаточно данных» (F1 0,191) и чаще рекомендуют то, что эталон запрещает: 39 из 152 рекомендаций (25,7 %). Правила оставлены как предфильтр, страховка и резервный режим |
| **Почему не вариант 3** | Модель без проверки ограничений хуже правил: zero-shot — macro F1 0,538, few-shot — 0,487; few-shot редко использует класс «нет данных» (F1 0,229 против 0,191 у правил, но 0,680 у D2), пропускает кандидатов в ответе и отбрасывает подходящих из-за несовпадения активности |
| **Почему не вариант 4** | Своя открытая модель стоит ≈ $109/мес (CPU) или ≈ $288/мес (GPU) против ≈ $0,46/мес за API при прогнозе 1 350 запросов. Точка безубыточности — 323 тыс. запросов/мес для CPU (в 239 раз больше прогноза; сервер успевает лишь ≈ 130 тыс.) и 855 тыс. для GPU. На Render модель не запустить: 512 МБ ОЗУ против ≈ 5 ГБ. Вариант пересматривается только если передача анкеты внешнему провайдеру будет признана недопустимой — тогда вопреки цене |
| **Персональные данные и площадка** | Провайдеру уходят анкета без имени, текст чата после удаления телефонов и e-mail, карточки кандидатов. ФИО, телефон, e-mail и заявки не передаются. Groq обрабатывает данные вне РК: до работы с реальными пользователями нужно согласие на обработку ПД с пунктом об ИИ-сервисе и проверка требований закона РК о трансграничной передаче. Выбор площадки определяется этим, а не ценой инференса |
| **Последствия: положительные** | Понятный и проверяемый подбор с объяснениями; класс «нет данных» распознаётся (F1 0,680 против 0,191 у правил); D2 лучше правил по F1 каждого класса; чуть меньше рекомендаций, запрещённых эталоном (23,6 % против 25,7 %); стоимость эксплуатации ≈ 207 ₸/мес; сайт не зависит от доступности модели |
| **Последствия: отрицательные** | Ранжирование хуже правил (NDCG@5 0,604 против 0,853) — модель отбрасывает подходящих; доля нарушений 23,6 % при пороге 2 %; в категории «ограниченное время» нет ни одной верной рекомендации. Бесплатный тариф Groq выдерживает ≈ 50 подборов в сутки и 2 в минуту — для реальной нагрузки нужен платный тариф. Провайдер не гарантирует детерминированность (20 разных system_fingerprint за прогон few-shot). Прежний эталон подготовлен автоматически, происхождение эталона v2 не подтверждено — ни один из них не является подтверждённой независимой человеческой разметкой. Зависимость от тарифов провайдера (llama-3.1-8b-instant в 2026 году уже переведена на «Contact Sales») |
| **Критерий пересмотра** | Вернуться к решению после промпта v3, Structured Outputs и правила «собака + меньше часа в день»: функция включается для пользователей, если на новом наборе из ≥ 30 сценариев с ручной разметкой двумя людьми D одновременно даёт macro F1 ≥ 0,75 и лучше baseline по F1 каждого класса, NDCG@5 не ниже baseline, нарушений ≤ 2 %, среднее время ≤ 5 с. После включения: если через 2 месяца конверсия из рекомендаций в заявку выросла меньше чем на 15 % относительно первых 4 недель, или доля резервного режима > 10 %, — функция отключается переключателем |
